# zig-todo 开发优先级计划


| 项    | 内容                      |
| ---- | ----------------------- |
| 策略   | 垂直切片：先打通「可运行的最小闭环」，再加能力 |
| 文档版本 | v0.1                    |


---

## 1. 总览

```text
P0 脚手架 + Hello CLI
P1 MVP：add / list / done / rm + JSON 持久化
P2 v1：edit / 优先级 / 标签 / 过滤 / --json
P3 体验与工程化：配置、原子写加固、测试与 CI、文档
P4 Backlog：归档、导入导出、截止日期、TUI…
```

原则：

1. **每阶段都可演示**：结束时有可运行二进制
2. **先测领域，再测 IO**
3. **不做提前抽象**：接口在第二次实现出现时再抽

---

## 2. 阶段详情

### P0 — 项目脚手架（约 0.5–1 天）

**目标**：能 `zig build` 出可执行文件，并打印帮助/版本。


| 任务                                   | 产出      | 完成标准           |
| ------------------------------------ | ------- | -------------- |
| 初始化 `build.zig` / `build.zig.zon`    | 构建系统    | `zig build` 成功 |
| `main.zig` 入口 + `version` / `--help` | CLI 骨架  | 本地运行可见帮助       |
| 目录骨架 `cli/` `domain/` `storage/`     | 空模块可编译  | 分层目录就位         |
| 根 `README.md`                        | 构建与运行说明 | 新人可按文档跑起来      |


**不做**：业务逻辑、持久化。

---



### P1 — MVP 闭环（约 2–4 天）

**目标**：日常「记一下 / 看一下 / 勾掉 / 删掉」可用。


| 优先级  | 任务                             | 依赖        |
| ---- | ------------------------------ | --------- |
| P1.1 | Domain：`Todo` + `TodoList`（内存） | P0        |
| P1.2 | Storage：读写 `todos.json`（可先非原子） | P1.1      |
| P1.3 | `add` / `list` / `done` / `rm` | P1.2      |
| P1.4 | 数据目录解析（默认路径）                   | P1.2      |
| P1.5 | Domain 单测 + 临时目录存储测            | P1.1–P1.3 |
| P1.6 | 错误与退出码初版                       | P1.3      |


**验收场景**：

```bash
zig-todo add "first task"
zig-todo add "second"
zig-todo list
zig-todo done 1
zig-todo rm 2
zig-todo list --status all
```

**退出 P1 的定义**：上述命令在重启进程后结果仍正确。

---



### P2 — v1 功能完整（约 2–3 天）

**目标**：达到产品文档中的 v1 能力。


| 优先级  | 任务                              | 说明            |
| ---- | ------------------------------- | ------------- |
| P2.1 | `edit` / `show` / `undone`      | 补齐读写路径        |
| P2.2 | `priority`（add/edit/list 过滤）    | `-p high`     |
| P2.3 | `tags`（多标签 + `--tag` 过滤）        | `-t a -t b`   |
| P2.4 | `list` 过滤组合：status/priority/tag | Domain filter |
| P2.5 | `--json` 输出                     | 脚本友好          |
| P2.6 | `clear --done`                  | 批量清理          |
| P2.7 | schema `version` + 简单迁移框架       | 为格式演进铺路       |


**验收场景**：

```bash
zig-todo add "写文档" -p high -t docs -t cli
zig-todo list --priority high --tag docs
zig-todo edit 1 -d "写产品与架构文档"
zig-todo list --json
zig-todo clear --done
```

---



### P3 — 工程化与体验（约 1–2 天）


| 任务                      | 说明                 |
| ----------------------- | ------------------ |
| 原子写 + `.bak`            | 降低损坏风险             |
| 表格对齐与空状态文案              | 提升可读性              |
| `--data-dir` / 环境变量     | 可测试、可多清单实验         |
| 更多单测与基础集成测              | 覆盖损坏 JSON、NotFound |
| CI 草稿（GitHub Actions 等） | build + test       |
| 完善 README（安装、命令速查）      | 对外可用               |


**退出 P3**：可作为「个人日常使用」版本。

---



### P4 — Backlog（按需）

按价值排序建议：

1. 导入 / 导出 JSON
2. 截止日期字段与 `list --overdue`
3. 已完成归档文件（控制主文件体积）
4. 文件锁（多终端同时用）
5. 交互 TUI
6. Windows 路径与测试矩阵

## 4. 人员与节奏建议


| 模式   | 建议                    |
| ---- | --------------------- |
| 单人业余 | 按 P0→P1→P2 每周一个阶段     |

| 评审点  | P1 结束做一次架构回顾（目录是否需拆分） |


---



## 5. 风险与缓冲


| 风险             | 应对                      |
| -------------- | ----------------------- |
| Zig 版本不熟导致构建卡壳 | P0 单独留足时间，先跑通官方 init 模板 |
| 参数解析耗时超预期      | P1 只支持最少 flag，复杂解析推到 P2 |
| 过早优化存储         | 坚持 JSON 到 P3；性能问题用基准说话  |
