# zig-todo 技术架构设计

| 项 | 内容 |
| --- | --- |
| 语言 | Zig（建议锁定当前稳定版，在 `build.zig` / CI 中写明） |
| 构建 | `build.zig` + `build.zig.zon` |
| 形态 | 单二进制 CLI |
| 文档版本 | v0.1 |

---

## 1. 架构目标

| 目标 | 做法 |
| --- | --- |
| 清晰分层 | CLI → Application → Domain → Storage |
| 可测 | Domain / Application 不依赖终端与真实文件系统（通过接口注入） |
| 可靠持久化 | 原子写 + 版本化 schema |
| 可演进 | 存储格式带 `version`，提供迁移钩子 |
| 依赖可控 | MVP 零第三方依赖；后续按需引入 |

---

## 2. 逻辑分层

```text
┌─────────────────────────────────────────┐
│                 CLI 层                   │
│  参数解析 / 帮助 / 输出格式化 / 退出码     │
└───────────────────┬─────────────────────┘
                    │ CommandRequest
┌───────────────────▼─────────────────────┐
│             Application 层               │
│  用例编排：Add / List / Done / Edit …    │
└───────────────────┬─────────────────────┘
                    │ Domain API
┌───────────────────▼─────────────────────┐
│               Domain 层                  │
│  Todo / TodoList 规则、校验、过滤、排序   │
└───────────────────┬─────────────────────┘
                    │ Store trait/interface
┌───────────────────▼─────────────────────┐
│              Storage 层                  │
│  读写、锁、原子替换、schema 迁移          │
└─────────────────────────────────────────┘
```

### 2.1 各层职责

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| **CLI** | 解析 argv、映射 flag、打印表格/JSON、映射错误到退出码 | 不写业务规则、不直接拼文件格式 |
| **Application** | 打开 store、调用领域操作、提交变更 | 不关心终端排版细节 |
| **Domain** | 实体、不变量、过滤排序、ID 分配策略 | 不碰 IO |
| **Storage** | 序列化、原子写、备份/迁移 | 不实现「完成任务」等业务语义 |

依赖方向：**只允许向下依赖**。

## 4. 核心模块设计

### 4.1 Domain：`Todo`

```zig
// 概念示意（非最终代码）
pub const Priority = enum { low, medium, high };
pub const Status = enum { open, done };

pub const Todo = struct {
    id: u64,
    text: []const u8,
    status: Status,
    priority: Priority,
    tags: []const []const u8,
    created_at: i64,      // unix seconds
    updated_at: i64,
    completed_at: ?i64,
};
```

不变量（Domain 强制）：

- `text` 去除首尾空白后非空，长度有上限（如 1024）
- `done` 时 `completed_at` 必有值；`open` 时为 `null`
- `tags` 规范化：小写、去重、禁止空标签

### 4.2 Application：用例伪代码

```text
AddTodo(store, input):
  list = store.load()
  todo = domain.create(list.nextId(), input, now())
  list.add(todo)
  store.save(list)
  return todo
```

所有写操作：**load → mutate → save**；后续若需并发，再引入文件锁。

### 4.3 Storage：接口

```zig
pub const Store = struct {
    // 函数指针或 vtable，便于 FakeStore 单测
    load: *const fn (*Store, Allocator) anyerror!TodoList,
    save: *const fn (*Store, TodoList) anyerror!void,
};
```

MVP 实现：`JsonFileStore`（单 JSON 文件）。

### 4.4 原子写流程

```text
1. 写入 data.json.tmp
2. fsync（若平台支持且有必要）
3. rename → data.json
4. 可选：保留 data.json.bak 上一份成功快照
```

崩溃时：要么旧文件完整，要么新文件已替换；避免半写 JSON。

### 4.5 数据路径

优先级：

1. `--data-dir`
2. 环境变量 `ZIG_TODO_DATA_DIR`
3. 平台默认目录（见产品文档）

文件：`<data-dir>/todos.json`

## 5. CLI 解析策略

### 5.1 MVP

手写轻量解析（子命令 + 少量 flag），控制依赖与学习成本。

建议约定：

- 全局 flag 在子命令前或任意位置二选一，**选一种并文档化**（推荐：全局 flag 可在任意位置）
- 位置参数：`add` 的文本；`done/rm/show/edit` 的 id

### 5.2 后续

若 flag 组合变复杂，再评估引入社区 argparse 库；架构上把解析结果收敛为：

```zig
pub const Command = union(enum) {
    add: AddArgs,
    list: ListArgs,
    done: IdArgs,
    // ...
};
```

CLI 只产出 `Command`，Application 只消费 `Command`。

## 6. 错误模型

统一错误枚举（示意）：

| 错误 | 来源 | 退出码 |
| --- | --- | --- |
| `InvalidArgs` | CLI | 2 |
| `NotFound` | Domain/App | 1 |
| `ValidationFailed` | Domain | 1 |
| `IoError` | Storage | 3 |
| `CorruptData` | Storage | 3 |
| `UnsupportedVersion` | Storage/migrate | 3 |

CLI 层将错误转为用户消息，不把 Zig 错误联合类型细节泄漏给用户。

## 7. 序列化格式选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| JSON 单文件 | 可读、易调试、易备份 | 并发弱、大文件时全量读写 | **MVP / v1 采用** |
| SQLite | 查询强、并发更好 | 依赖/绑定成本高 | 远期可选 |
| 自定义二进制 | 紧凑快 | 难调试、迁移成本高 | 不优先 |

千级任务规模下，全量 JSON 足够。

Schema 见 [04-数据模型设计](./04-数据模型设计.md)。

## 9. 并发与安全边界

| 主题 | MVP 决策 |
| --- | --- |
| 多进程同时写 | 不保证；后续加 `flock` / 锁文件 |
| 路径遍历 | `--data-dir` 不做沙箱，信任本机用户 |
| 文本注入 | 输出时注意控制字符；JSON 用标准转义 |

## 11. 技术风险与缓解

| 风险 | 缓解 |
| --- | --- |
| Zig 版本语法变动 | 文档与 CI 锁定版本；`build.zig.zon` 记录 |
| 手写 argv 解析变复杂 | Command 联合类型边界清晰，可整体替换解析器 |
| JSON 损坏 | 原子写 + bak；启动时校验并给出修复指引 |
| 大列表性能 | v1 前做简单基准；必要时索引或换存储 |
